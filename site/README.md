# site

The Worker on `splitlane.dev`: the project's website, and the phone page's
old address sent on to [`app.splitlane.dev`](../web/README.md).

| Path | What lives there |
|---|---|
| `src/index.js` | The Worker's entry: exports the handler and nothing else |
| `src/site.js` | The redirect from `/app`, the site's Content Security Policy, and the handler that applies both |
| `public/` | The site's files, served as static assets through the Worker |
| `public/css/site.css`, `public/js/site.js` | The one stylesheet and the one script every page uses |
| `public/img/`, `public/fonts/` (and `public/video/` once there are videos) | Generated by `tools/build-media.sh`; do not edit by hand |
| `tools/build-media.sh` | Rebuilds images, icons and fonts from `assets/` and `src-app/assets/fonts/` |
| `tools/video-slot.mjs` | Puts an encoded clip into one of the page's video slots |
| `tools/posts.mjs` | The blog's posts and their publication dates; writes a changed date into every file that carries it |
| `test/` | `node --test`: the redirect, the policy on every served file, the 404 page, no third-party URLs, byte ranges on videos, the video slots |

## The phone page's old address

The phone's page used to be at `splitlane.dev/app` and is now at
`app.splitlane.dev`, so `/app` and everything under it redirect there.

| Old address | New address |
|---|---|
| `/app`, `/app/`, `/app/index.html` | `https://app.splitlane.dev/?moved` |
| `/app/<file>` | `https://app.splitlane.dev/<file>` |

Desktop builds from before the move print and QR-encode
`https://splitlane.dev/app#pair=...`. The fragment is never sent to a server,
and a browser carries it across a redirect whose `Location` has none, so such
a link opens the new page ready to pair. `?moved` makes the page say why a
phone paired on the old address has to pair again: a browser keeps storage
per origin, so the old pairing stays behind. The redirect also sends
`Clear-Site-Data` to wipe that storage, since the site that took this origin
over runs scripts of its own.

## The site

Plain HTML and CSS in `public/`, no framework and no build step for the
pages. `wrangler.toml` serves the directory with `run_worker_first = true`,
so every request passes through the Worker: the redirect keeps answering
`/app` whatever files the site has (nothing may be served under `/app`), and
every other response, pages and assets alike, gets the site's policy.
`html_handling = "auto-trailing-slash"` serves `compare/index.html` at
`/compare/`; `not_found_handling = "404-page"` answers a missing path with
`public/404.html` and status 404.

That policy (`SITE_CSP` in `src/site.js`) is strict on purpose: scripts,
styles, fonts and media from `splitlane.dev` only, nothing inline, no
third-party script. It is policy, not a stopgap. For the pages that means:

- no `<script>` without `src`, no `<style>` element, no `style="..."`
  attribute and no `on...=` handler: the browser would refuse them;
- fonts are self-hosted (`public/fonts/`, the app's own Geist);
- video is our own file in a `<video>` element, never an embed;
- the page works without its script: `public/js/site.js` only adds a Copy
  button and plays videos while they are on screen.

The keys a phone paired on the old page left in this origin's storage are
dead once the computer updates: the release that moved the page revokes
every pairing made before it on its first start. They stay in storage until
the phone opens `/app` again and its browser honours `Clear-Site-Data`
(Safari does not), and on Android an installed page shares that storage with
Chrome, so a computer not yet updated would still answer a script that used
them. Beyond that, this origin was the page's: people have its address on
their phones and in old pairing codes, and the site has no need to run
anyone else's code. The Worker sets the header itself, so a `_headers` file
cannot override it.

### Adding a page

Copy the `<head>` of an existing page and change its title, description,
canonical and `og:url`. Add the page to `public/sitemap.xml`. A blog post
also goes into the list on `public/blog/index.html` and into
`public/blog/feed.xml`, and its slug, title, description and date into
`POSTS` in `tools/posts.mjs`. That list is the one place a post's date is
set: change it there and run `node tools/posts.mjs` to write it into the
page, the list, the feed and the sitemap. The tests check that each page has its meta, is in
the sitemap, and that every file it refers to exists.

### Images and video

Screenshots come from `assets/images/` as WebP in several widths; a page
picks one with `srcset` and the light or dark one with
`<picture><source media="(prefers-color-scheme: dark)">`. Each sits in a
`<figure class="media r-desktop">` (or `r-wide`, `r-phone`), which fixes its
aspect ratio, so a section's screenshot can be replaced by a video of the
same size without moving anything:

```html
<figure class="media r-desktop">
  <video data-autoplay muted loop playsinline controls preload="none"
    width="1280" height="890" poster="/video/<name>-poster.webp">
    <source src="/video/<name>.mp4" type="video/mp4">
  </video>
</figure>
```

After changing a source image, run `tools/build-media.sh` (it needs `cwebp`,
`ffmpeg`, ImageMagick and `pyftsubset`) and commit what it writes. For a
video, `tools/build-media.sh --video <recording.mp4> <name> [poster-second]`
writes `public/video/<name>.mp4` and `<name>-poster.webp`; recordings
themselves stay out of the repository.

The places on the home page where a clip will replace a screenshot carry
`data-video-slot`: `hero`, `state`, `grid`, `fleet` (an `r-wide` frame) and
`host` (today a panel of facts). The clips come from
`scripts/record-demo/`, which names them after their slot. Encode each as
`<slot>-dark` and, where there is one, `<slot>-light`, then:

```bash
tools/build-media.sh --video <run-dir>/assets/hero.mp4 hero-dark 3
node tools/video-slot.mjs hero      # --check prints the markup, writes nothing
```

The tool writes the markup above into the slot, with the slot's own
description for screen readers. With a light clip as well, `<source media>`
picks the clip by theme and `public/js/site.js` picks the poster.

Videos under `/video/*.mp4` are served with byte ranges by the Worker
(`withRange` in `src/site.js`). Safari plays a `<video>` only from a server
that answers `Range` with 206, and the asset binding answers it with the
whole file and 200, so the Worker cuts the range from the file itself.

## Preview

```bash
cd site
npx wrangler@4.145.0 dev
```

Local only: it serves the Worker and `public/` at `http://localhost:8787`.

## Test

```bash
cd site
node --test
```

## Deploy

```bash
npx wrangler@4.145.0 deploy
```

This puts the site live on `splitlane.dev`, together with the redirect. Then
check that the zone adds no script of its own to the pages (Cloudflare Web
Analytics does when it is switched on for the zone, and the policy would
block it): `curl -s https://splitlane.dev/ | grep -c cloudflareinsights`
should print `0`.
